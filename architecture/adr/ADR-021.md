# ADR-021 — Deterministic Runtime Execution Trace Boundary

## Status

Accepted

## Context

EOS separates decision execution, immutable event journaling, external command
dispatch, and next-tick progression. These boundaries preserve deterministic
ownership, but callers also need to observe the exact identity relationships
across one completed lifecycle.

Adding diagnostic state to JournaledEMSRuntime or persisting lifecycle data
inside the kernel would make runtime behavior stateful and couple observation
to storage.

## Decision

Introduce immutable, slotted RuntimeExecutionTrace with exact references to:

- source JournaledEMSTick;
- dispatched DispatchedJournaledEMSTick; and
- progressed JournaledEMSTick.

Provide `RuntimeExecutionTrace.create` for already-completed lifecycle objects.
Validate that the dispatched tick retains the exact source tick and that the
progressed journal preserves source EventRecord identities as its prefix.

Do not call any runtime, policy, command, or journal mutation boundary during
construction. Generate no timestamp, UUID, telemetry, or log entry.

## Consequences

- Completed runtime lifecycles gain one deterministic observation value.
- Tick, result, journal, command, event, and record identities remain intact.
- Invalid or incomplete lifecycle relationships cannot produce a valid trace.
- Each lifecycle owns a separate immutable trace with no shared trace state.
- Runtime execution remains stateless and unchanged.

## Why Trace Is Not Runtime State

The trace is created after lifecycle completion and has no role in future
decisions, dispatch, sequence allocation, or progression. It observes state
transitions without owning them.

## Why Trace Does Not Persist

Storage, serialization, retention, and recovery are separate infrastructure
concerns. Keeping them outside RuntimeExecutionTrace preserves the kernel's
deterministic and side-effect-free observation boundary.

## Alternatives Considered

- Add trace fields to runtime: rejected because runtime must remain stateless.
- Recompute lifecycle objects from policy and context: rejected because it would
  violate identity and side-effect boundaries.
- Store copied snapshots or dictionaries: rejected because copies lose exact
  object relationships.
- Persist traces automatically: rejected because persistence ownership and
  failure semantics are not defined.
