# ADR-022 — Deterministic Replay Boundary

## Status

Accepted

## Context

RuntimeExecutionTrace preserves the exact immutable objects from one completed
decision, journal, dispatch, and progression lifecycle. Callers need a stable
way to inspect that observation repeatedly without rerunning policy logic or
external command effects.

Treating replay as re-execution would risk duplicate commands, new events,
changed journals, and non-deterministic external behavior.

## Decision

Introduce:

- immutable, slotted ReplayResult containing exact source, dispatched, and
  progressed tick references; and
- stateless RuntimeReplay with `replay(trace)`.

Replay validates the RuntimeExecutionTrace input and returns a new immutable
observation wrapper around the exact lifecycle objects. ReplayResult
defensively validates the identity chain.

Replay calls no EMSPolicy, runtime tick, progression, dispatcher,
CommandExecutor, or EventJournal mutation method. It generates no timestamp,
UUID, event, journal, cache, or telemetry.

## Replay Is Not Re-execution

Replay is deterministic observation of an already completed lifecycle. It
never attempts to reproduce the side effects that originally created the
trace.

## Consequences

- Completed lifecycle observations can be inspected repeatedly.
- Exact tick, result, journal, command, event, and EventRecord identities remain
  intact.
- Broken or fabricated identity chains are rejected.
- Runtime execution and external devices remain untouched.
- Persistence and recovery remain separate future concerns.

## Alternatives Considered

- Re-evaluate the policy: rejected because it creates a new decision rather than
  replaying an observation.
- Re-dispatch commands: rejected because replay must not duplicate external
  effects.
- Copy lifecycle objects: rejected because copies lose exact identity.
- Append replay events: rejected because observation must not mutate journals.
- Persist replay results: rejected because persistence ownership is outside this
  boundary.
